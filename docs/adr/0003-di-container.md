# ADR-0003: контейнер dig в точке сборки

Дата: 2026-10-25.
Статус: принято.

## Контекст

Задание требует DI-контейнер.
Сервис парка уже принимает зависимость через конструктор.
Бизнес-логика должна сохранять возможность прямой сборки в тестах.

## Решение

Использовать `go.uber.org/dig v1.19.0` в `internal/app`.
`BuildFleet` создаёт локальный контейнер и регистрирует два конструктора.
`dig.As` предоставляет базовый техосмотр как интерфейс `ServiceCenter`.
`Invoke` получает собранный `*FleetService`.
Ошибки регистрации и сборки возвращаются вызывающему коду.

Пакеты `domain` и `service` не импортируют контейнер.
Тесты парка создают сервис через обычный конструктор с fake.

## Альтернативы

- Ручная сборка проще для двух зависимостей, но не выполняет требование о контейнере.
- Собственный контейнер добавил бы код, не относящийся к учёту транспорта.
- Передача контейнера сервисам скрыла бы их зависимости.

## Последствия

Конфигурация DI проверяется отдельными интеграционными тестами.
Каждый вызов `BuildFleet` создаёт независимый парк.
Проект получает одну внешнюю зависимость с закреплённой версией.
Её допустимость нужно согласовать, если преподаватель применяет правило шаблона о сторонних библиотеках.
