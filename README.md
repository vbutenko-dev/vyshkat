## Запуск

Установите [Go](https://go.dev/doc/install) версии не ниже 1.22.
Откройте терминал в папке проекта:

```sh
go mod download
go run ./cmd/vyshkat
```

Данные хранятся в памяти и исчезают после завершения программы.
Каждый ответ вводится отдельной строкой. Для дробной энергии используйте точку, например `1.5`.

| Команда | Результат |
| --- | --- |
| `1` | Добавление электросамоката, велосипеда или электровелосипеда |
| `2` | Добавление шлема или зарядной станции |
| `3` | Количества объектов и суточное энергопотребление |
| `4` | Принятый транспорт с оценкой простоты не ниже 6 |
| `5` | Названия и инвентарные номера всех объектов на балансе |
| `0` | Завершение работы |

При числовой опечатке программа повторяет вопрос.
Если заполненная карточка нарушает правила, программа показывает ошибку и возвращается в меню.
Конец ввода завершает работу. Незавершённая карточка не добавляется.

## Правила учёта

Название и инвентарный номер обязательны. Конструкторы удаляют пробелы по краям этих строк.
Номер уникален для транспорта и вещей вместе. Сравнение учитывает регистр.
Оценка простоты находится в диапазоне 1–10.
Энергопотребление задаётся конечным неотрицательным числом в кВт·ч за сутки.

`FleetService` проверяет данные и свободный номер, затем запрашивает решение `ServiceCenter`.
Базовый техосмотр принимает исправный транспорт и отклоняет неисправный с причиной.
Парк добавляет транспорт только при положительном решении.
Отказ не меняет коллекции и не резервирует номер.
Вещи проходят проверку данных и номера без техосмотра.

Электросамокат, электровелосипед и зарядная станция реализуют `EnergyConsumer`.
Велосипед и шлем увеличивают количество объектов, но не потребление энергии.
Общая энергия включает транспорт и вещи. Отчёт также показывает эти суммы отдельно.
Расход станции означает её собственные затраты и не включает повторно расход транспорта.
Это принятая трактовка учебного отчёта.

Список для новичков содержит только принятый транспорт с простотой от 6 до 10.
Порядок совпадает с порядком приёмки. Вещи в список не входят.

## Архитектура

| Пакет | Ответственность |
| --- | --- |
| [internal/domain](internal/domain) | Интерфейсы, структуры и проверка характеристик в конструкторах |
| [internal/service](internal/service) | Техосмотр, приёмка, хранение и отчёты |
| [internal/app](internal/app) | Сборка зависимостей через `go.uber.org/dig` |
| [internal/console](internal/console) | Меню, чтение ответов и отображение результатов |
| [cmd/vyshkat](cmd/vyshkat) | Запуск приложения и обработка ошибки завершения |

`InventoryItem` задаёт название и номер. `Vehicle` добавляет простоту и исправность.
`EnergyConsumer` отдельно задаёт суточный расход энергии.
Типы удовлетворяют интерфейсам автоматически, когда имеют нужные методы.
Общие данные включены в структуры через композицию.

Конструкторы проверяют отдельную карточку.
`FleetService` повторно проверяет переданные реализации интерфейсов и обеспечивает уникальность номера.
Его конструктор принимает интерфейс `ServiceCenter`.
Контейнер `dig v1.19.0` создаёт настоящий техосмотр и передаёт его парку.
Пакеты модели и сервисов не обращаются к контейнеру.

В тестах вместо настоящего техосмотра передаётся fake с заранее заданным решением.
Поэтому приёмку можно проверить отдельно от алгоритма осмотра и конфигурации контейнера.
Подробнее: [ADR-0002](docs/adr/0002-inspection-dependency.md) и [ADR-0003](docs/adr/0003-di-container.md).

## SOLID и ответы на вопросы задания

| Принцип | Применение |
| --- | --- |
| SRP | Модель проверяет характеристики, техосмотр принимает решение, парк ведёт учёт, консоль обрабатывает ввод и вывод. |
| OCP | Приёмка и отчёты работают с интерфейсами. Тесты добавляют новый вид транспорта без изменения сервисов. |
| LSP | Виды транспорта соблюдают контракт `Vehicle`. Общие проверки требуют корректных данных и простоты 1–10. |
| ISP | Энергопотребление отделено от инвентаризации. Велосипед и шлем не реализуют ненужный им `EnergyConsumer`. |
| DIP | Парк зависит от интерфейса `ServiceCenter`. Вызывающий код выбирает настоящую реализацию или fake. |

**Где принцип проявляется наиболее явно?**
DIP виден в `NewFleetService(center ServiceCenter)`.
[Тест приёмки](internal/service/fleet_test.go) меняет решение fake без изменения кода парка.

**Где есть сознательное ограничение?**
Меню [input.go](internal/console/input.go) перечисляет поддерживаемые конструкторы.
Для нового вида потребуется дополнить меню. Для пяти учебных типов этот подход проще отдельной системы регистрации.
Приёмка и отчёты при этом продолжают работать через интерфейсы.

**Как расширить модель?**
Новый транспорт реализует `Vehicle` и при необходимости `EnergyConsumer`.
Учёт сотрудников следует добавить отдельно: сотрудник не является инвентарным объектом.
Для склада понадобятся остатки и перемещения. Сейчас приложение учитывает только отдельные объекты с номерами.

**Какие решения проверяют тесты и как подменяется зависимость?**
Тест настоящего техосмотра проверяет исправность для всех видов транспорта.
`TestFleetFollowsInjectedInspectionDecision` проверяет следование решению fake.
`TestBeginnerVehiclesThresholdOrderAndIndependentList` проверяет границу 5/6 и порядок результата.
Fake реализует `Inspect`, возвращает заданный результат и запоминает вызовы.

**Каков вклад ИИ и автора?**
ИИ подготовил код, тесты и документацию в ходе учебного диалога.
Автор выбрал Go, задавал вопросы, определял следующие этапы и формат сдачи.
Подробности и ограничения оценки вклада указаны в [AI_USAGE.md](AI_USAGE.md).

## Проверка

Выполните из корня проекта:

```sh
go test -v ./...
go vet ./...
go build ./...
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
go run ./cmd/vyshkat < examples/demo.txt
```

Тесты проверяют конструкторы, отказ техосмотра, дубликаты, отчёты, DI и консольный ввод.
Консольные тесты передают `strings.Reader` и `bytes.Buffer`, поэтому не требуют ручного ввода.
Границы, `NaN`, бесконечность, конец ввода и ошибки чтения проверяются отдельными случаями.
